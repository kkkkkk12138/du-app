# 渡：产品扩展与数据真实性记录

本文件记录原型中已有视觉位置、但当前数据模型尚不支持的能力。它们不是当前版本的模拟数据，也不代表已经实现。

## 数据真实性原则

1. 日期、时间、农历、节气、天气、地点、统计和计数必须来自真实计算、系统能力或持久化数据。
2. 不得用常量、随机数、开发 Seed 或示例文案冒充生产环境的实时返回值。
3. 数据源不可用时，隐藏对应内容或展示明确的空状态，不伪造“看似完整”的结果。
4. 开发 Seed 只用于 Debug 验收，必须与正式用户数据隔离。
5. 新能力必须先定义数据来源、Schema、写入时机、迁移方案和隐私边界，再接入 UI。

## Daily 照片卡底栏计数

**原型位置**

`daily.html` 的照片卡底栏包含 `❤ 12`。

**当前状态**

- `Memory` 表没有与该数字对应的字段或事件记录。
- 当前版本不显示该数字，也不会写死 `12`。
- 照片卡底栏的视觉结构可以保留，但只有存在真实数据时才渲染计数。

**产品边界**

`AI_CODING_TASK.md` 明确禁止社交点赞、评论和关注。因此该能力不能实现为他人点赞数。

**后期候选方向**

- 本地“回望次数”：用户主动再次打开某条日迹时累计。
- 私密“铭记标记”：用户主动收藏或标记某个此刻。
- 本地“共鸣次数”：仅记录用户自己的交互，不产生社交关系。

**实现前置条件**

- 明确最终产品语义和交互入口。
- 选择新增 `Memory` 聚合字段或独立事件表。
- 计数只能由真实用户操作产生。
- 增加数据库迁移、Repository、测试和隐私说明。
- 明确卸载、同步、恢复与多设备合并策略。

## 锚点时刻统计

“这一天你写了 N 条，是本月最多”已使用 WatermelonDB 中的日迹记录实时聚合，不使用原型固定数字。没有足够记录时，应显示真实数量或省略比较结论。

## 时间与历法

Daily 的公历、农历、节气、宜忌和跨日刷新必须动态生成。HTML 原型中的示例日期仅作为视觉参考，不作为 App 的固定内容。

## 详情页返工边界

**用户反馈**

- Daily 点击此刻后的旧详情浮卡不满意；新设计规范已提供并完成恢复开发。
- 信箱拆信后的旧原信页信息密度与空间关系偏逼仄，且与新版 Daily 详情
  的暖纸调性脱节。
- 原信页曾出现模态栈残留、返回按钮被全屏内容层遮挡等问题。

**当前边界**

- `MemoryDetailModal.tsx` 已解除冻结，视觉与交互基线为
  `/Users/bytedance/memory-detail-dev-spec.md`。
- `UnsealScreen.tsx` 已按用户的新要求解除冻结。已拆后的阅读状态改为
  全屏暖纸信笺，与 Daily 详情共享颜色、字体和附件语汇。
- 返回操作使用最高交互层的固定顶栏，并显式 `popTo` 来源 Tab，避免依赖
  残留模态栈。
- Daily 详情创建的回信必须同时出现在信箱“已拆”，打开后读取
  `reply_memory_id` 对应的回信正文；父日记仍保留原回信串。

**返工时必须保留**

- 真实正文、照片、录音、手书、坐标、标签和时间数据。
- 信件未拆/已拆状态、来源返回、写回信、放回日迹和减弱动态效果。
- 遮罩关闭、显式关闭、Android 返回键及至少 44pt 的可点击热区。
- 不伪造地图、地点、天气或信件内容。

**返工验收重点**

- 先确定详情页的信息层级和容器形态，再设计视觉。
- 小屏设备不得挤压状态栏、正文和底部操作区。
- 所有覆盖层必须验证绘制顺序与触摸命中，避免“可见但点不到”。
